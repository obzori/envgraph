# Безопасность

envgraph спроектирован так, чтобы его можно было безопасно запускать в любом
репозитории, но у детектора секретов есть известные ограничения. На этой
странице точно описано, что программа читает, пишет и гарантирует.

## Что читает envgraph

- Файлы исходного кода в рабочей директории с расширениями `.js`, `.jsx`,
  `.ts`, `.tsx` (кроме `node_modules`, `.git`, `dist`, `build`) — только
  разбор в AST.
- Ваш файл `.env` при запуске `envgraph create example`.
- Во время `scan`: только **имена** файлов `.env*` (`.env`, `.env.local`, …) —
  содержимое никогда не читается, значения не попадают в вывод.

### БЕЗ СЕТЕВОГО ДОСТУПА! БЕЗ ТЕЛЕМЕТРИИ!

envgraph никогда не выполняет сетевые запросы и не собирает телеметрию.

## Что записывает envgraph

- Только один файл: `.env.example` в рабочей директории, и только когда вы
  явно запускаете `create example` (и подтверждаете перезапись, передаёте
  `--force` или файла ещё нет).

## Чего envgraph никогда не делает

Код вашего проекта не выполняется и не вычисляется. Файлы исходников только
разбираются через TypeScript compiler API; `.env` разбирается построчно.

## Исключение: файл конфигурации

Есть ровно одно исключение: ваш `envgraph.config.{js,ts,mjs,cjs}` — это
**JavaScript/TypeScript-файл, который выполняется** для чтения его экспортов.
Это та же модель, что у ESLint (`eslint.config.js`), Prettier
(`prettier.config.js`) или любого другого JS-инструмента — конфиг в формате
этого тула обязан быть кодом.

Это означает:

- Конфиг — это доверенный ввод. Кто может записать `envgraph.config.js` в
  проект, тот уже может записать в `package.json` (чей жизненный цикл
  выполняется при каждом `npm install`), в любой исходник или `.npmrc` —
  поэтому сам по себе конфиг не добавляет достижимого вектора атаки на вашей
  машине.
- Чтобы `envgraph.config.*` что-то передал наружу, атакующему нужен доступ на
  запись в репозиторий — а это уже полная компрометация. Сам envgraph никогда
  не открывает сетевых соединений.
- Для случая CJS-в-ESM-пакете исходник конфига выполняется напрямую (через
  `data:`-импорт и фолбэк на `vm`). Контекст `vm` **не является** границей
  безопасности — это лишь механизм выполнения, и его нельзя так трактовать.

Если вы запускаете envgraph на репозиториях, которым не доверяете (например,
сканирование непроверенного клона в CI), конфиг тоже выполняется. Безопасный
паттерн такой же, как для любого внешнего кода: запускайте в изолированном
одноразовом окружении (контейнер / эфемерный CI-раннер), а не на рабочей
машине.

## Эвристика имён секретов

Чувствительные переменные определяются исключительно **по имени**: если имя
переменной содержит (без учёта регистра) одну из этих подстрок, значение
заменяется пустым в `.env.example`:

`PASSWORD`, `PASS`, `SECRET`, `TOKEN`, `API_KEY`, `APIKEY`, `PRIVATE_KEY`,
`ACCESS_KEY`, `CLIENT_SECRET`, `AUTH_TOKEN`, `DATABASE_URL`, `DATABASE_URI`

Общие подстроки вроде `URL`, `KEY` или `ID` сами по себе сознательно *не*
являются шаблонами — например, `API_URL` сохраняется, несмотря на `URL`.

## Ограничения санитайзера

- Проверяются только **имена**, но не значения. Секрет под безобидным именем
  (например, `APP_CONFIG`) попадёт в `.env.example` как есть.
- Обратно, безобидные переменные могут быть очищены (например,
  `TOKEN_BUCKET_SIZE`).
- Новые типы имён креденшелов не распознаются, пока их шаблон не добавят в
  список.

**Поэтому: всегда проверяйте `.env.example` перед коммитом.** envgraph
печатает это предупреждение после каждой успешной генерации:

```text
IMPORTANT: CHECK .env.example BEFORE COMMITTING IT.
Make sure it does not contain passwords, tokens, API keys,
private keys, credentials, or other sensitive information.
```

Исключение из правил: ключи, указанные в `example.defaults` конфига,
записываются как есть — явное намерение пользователя важнее санитайзера.

Санитайзер снижает риск, но **не** гарантирует удаление секретов.

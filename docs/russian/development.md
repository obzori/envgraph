# Разработка

## Структура репозитория

```text
src/
├── index.ts # точка входа в публичный пакет (реэкспорт ниже)
├── cli/
│ ├── index.ts # диспетчеризация CLI, глобальные флаги (--minimal), скрипт bin
│ ├── ui.ts # общие примитивы пользовательского интерфейса: rule(), section(), banner()
│ ├── spinner.ts # простая анимация прогресса прокрутки с помощью точек (только для TTY)
│ ├── offload.ts # запуск чистой функции в рабочем потоке (поддерживает работу спиннера)
│ ├── prompt.ts # минимальное синхронное подтверждение y/N
│ ├── style.ts # цвет мела вспомогательные функции
│ └── commands/ # одна команда для папки на подкоманду + реестр (index.ts)
├── core/
│ ├── scanner/ # сканирование исходных файлов: ast.ts, scanner.ts
│ └── env/ # парсер .env, очиститель секретов, генератор примеров
├── analysis/ # API программного анализа (шаблон, см. limitations.md)
├── config/
│ ├── defaults.ts # типы + DEFAULT_CONFIG + вспомогательные функции слияния
│ ├── loader.ts # обнаружение envgraph.config, загрузка, кэширование
│ └── index.ts # реэкспорт (единый путь импорта для потребители)
├── output/ # форматирование вывода (json, table, mermaid)
└── filesystem/ # вспомогательные средства для обнаружения файлов и чтения .env
tests/ # наборы тестов node:test (cli, check, create, scan, …)
dist/ # вывод сборки (публикуется в npm)
```

## Настройка

Требования:

- Node.js **>= 22** (при разработке используется нативное удаление типов
  TypeScript для прямого запуска `src/*.ts`).

- npm.

```bash
npm install
```

Зависимости времени выполнения: `chalk` (цвета терминала) и `typescript` (парсинг AST).
Зависимости разработки: `@types/node`.

## npm скрипты

| Скрипт | Что он делает |

| --- | --- |

| `npm run build` | Компилировать TypeScript (`tsc`) в `dist/`. |

`npm run typecheck` | Проверить тип проекта, включая тесты (`tsconfig.test.json`). |

`npm test` | Запустить проверку типов, а затем набор тестов с помощью `node --test "tests/**/*.test.ts"`. |

`npm start` | Запустить CLI из исходного кода (`node src/cli/index.ts`). |

`npm run dev` | Запустить CLI из исходного кода с отслеживанием файлов. |

`npm run clean` | Удалить каталог `dist/`. |

`npm run prepublishOnly` | Очистить, собрать и протестировать (запускается автоматически при публикации). |

Попробуйте CLI локально на тестовом проекте:

```bash
npm start -- scan
npm start -- create example --dry-run
```

## Тестирование

Тесты используют встроенный [`node:test`](https://nodejs.org/api/test.html) раннер
— без зависимости от тестового фреймворка. Наборы тестов находятся в `tests/`:

- `cli.test.ts` — диспетчеризация CLI, справка/версия, неизвестные команды.

- `scan.test.ts` — обнаружение файлов, определение AST, группировка, обработка ошибок.

- `check.test.ts` — сравнение .env с использованием (отсутствующие/неиспользуемые/дубликаты).

- `create.test.ts` — анализ .env, очистка, генерация, флаги,
поведение перезаписи.

- `create-config.test.ts` — обнаружение конфигурации, слияние, темы, hasConfigKey. — `envfiles.test.ts`, `loaders.test.ts`, `output.test.ts` — основные строительные блоки.

Основная логика команд написана в виде чистых функций (например, `runScan`,
`runCheck`, `createExample`), которые возвращают результаты вместо записи в
поток процесса, поэтому тестам не требуется захват потока. Новый код должен следовать
этому шаблону; обертки, затрагивающие реальное состояние процесса, намеренно сделаны тонкими,
и сложными для тестирования, поэтому логику следует размещать в чистых функциях.

Запустите один набор тестов:

```bash
node --test tests/create.test.ts
```

## Вклад

1. Откройте или прокомментируйте [issue](https://github.com/obzori/envgraph/issues),

описывающий изменение.

2. Создайте форк/ветку, внесите свои изменения с тестами.

3. Убедитесь, что `npm test` проходит успешно, а `npm run build` компилируется без ошибок.

4. Создайте запрос на слияние с описанием изменений.

Сохраняйте соответствие изменений существующему стилю: табуляция для отступов,
комментарии JSDoc к экспортируемым функциям и ядра, состоящие из чистых функций, с тонкими CLI-обертками. Оформление пользовательского интерфейса (правила/баннеры) должно находиться в `ui.ts`; для представления каждой команды следует повторно использовать примитивы `ui.ts`, а не изобретать их заново.

## Архитектура команд

Каждая подкоманда разделена на крошечные модули с одной целью, поэтому изменение попадает
в один файл, а не в большую команду:

- `<name>.ts` — обертка команды (реализует `EnvGraphCommand`): обрабатывает
баннер, индикатор загрузки и вывод, а затем повторно экспортирует части, чтобы
существующие импорты продолжали работать.

- `<name>-flags.ts` — разбор аргументов (`--format`, `-o`, `--force`, …).

- `<name>-run.ts` — точка входа (`runScan`, `runCheck`), которая возвращает
результат. Именно это импортируют тесты.

- `<name>-report.ts` / `<name>-issues.ts` — логика рендеринга/анализа.

- `<name>-config.ts` / `<name>-example.ts` — логика генератора для `create`.

- `<name>-guard.ts` — общие проверки без побочных эффектов (например, ограничение на большой каталог,
которое используется совместно `scan` и `check`).

### Соглашения

1. **Логика чистая и проверяемая** — функции принимают простые аргументы и возвращают
объекты `Outcome` (`{ exitCode, stdout, stderr, … }`); они никогда не обращаются к
`process.stdout`/`stderr`.
